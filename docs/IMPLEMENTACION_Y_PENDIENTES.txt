4. IMPLEMENTACIÓN REALIZADA: ACADEMIA
======================================================================

4.1. Estructura educativa

Se construyeron dos rutas completas:

RUTA CLÁSICA, 8 módulos:

1. Tablero y notación.
2. Reglas y finales básicos.
3. Principios de apertura.
4. Táctica.
5. Ataque y defensa.
6. Estructuras de peones.
7. Finales.
8. Cálculo práctico.

RUTA CUÁNTICA, 8 módulos:

1. Modelo probabilístico.
2. Movimiento clásico.
3. Split o superposición.
4. Fusión.
5. Medición.
6. Túnel.
7. Entrelazamiento y enroque cuántico.
8. Estrategia y coherencia.

Cada módulo contiene cuatro actividades:

- Explicación conceptual.
- Práctica guiada.
- Puzle independiente.
- Examen sin pistas.

Total implementado: 16 módulos y 64 actividades bilingües.

El contenido está versionado, estructurado y validado con Zod. Cada intento
conserva la versión de contenido con la que se inició.

4.2. Diagnóstico y recomendación

- El diagnóstico es opcional.
- Evalúa varios módulos de la ruta seleccionada.
- El resultado inicial queda limitado a 60 puntos de dominio.
- Nunca sustituye la comprobación posterior mediante práctica real.
- El sistema recomienda la siguiente lección o un repaso vencido.
- También se permite navegación libre por el mapa dentro de las reglas de
  desbloqueo.

4.3. Puntuación y dominio

- Cada intento obtiene entre 0 y 100 puntos.
- Se tienen en cuenta corrección, pistas y acciones adicionales.
- Las pistas finales penalizan más que las iniciales.
- El dominio se actualiza mediante:

  nuevo = 0,7 x dominio anterior + 0,3 x puntuación del intento

- Para avanzar a un módulo posterior se requiere:

  - Dominio mínimo de 70.
  - Dos resoluciones correctas e independientes.

- El contenido completado nunca vuelve a bloquearse.
- Los eventos repetidos con el mismo UUID se ignoran de forma idempotente.

4.4. Repaso espaciado

- Intervalos de 1, 3, 7, 14 y 30 días.
- Un acierto avanza al siguiente intervalo.
- Un fallo retrocede un intervalo.
- La cola de repaso prioriza habilidades vencidas.
- El cuaderno de errores permite volver al último concepto fallado.

4.5. Escalera de pistas

Se implementaron cuatro niveles:

1. Orientación conceptual.
2. Foco sobre la zona o el riesgo relevante.
3. Reducción de candidatos.
4. Solución y explicación de consecuencias.

4.6. Modos educativos

- Ruta guiada adaptativa.
- Cola de repaso.
- Cuaderno de errores.
- Laboratorio diario determinista por fecha y ruta.
- Puzzle Sprint de 3, 5 y 10 minutos.
- Diagnóstico independiente para clásico y cuántico.

5. IMPLEMENTACIÓN REALIZADA: JUEGO Y VARIANTES
======================================================================

5.1. Modos preservados

- classic continúa utilizando chess.js.
- quantum-standard conserva el reglamento cuántico anterior.
- En modo cuántico no existe jaque ni mate.
- Capturar el rey rival produce la victoria.
- La ausencia de acciones legales produce tablas.

5.2. Coherencia limitada

Se añadió quantum-coherence como ruleset separado.

Reglas implementadas:

- Capacidad configurable de 2, 4 o 6.
- El valor previsto para competitivo es 4.
- Cada rama adicional consume una unidad.
- Un entrelazamiento de túnel activo consume una unidad adicional.
- El enroque cuántico requiere dos unidades libres.
- Las fusiones y colapsos liberan capacidad automáticamente.
- No hay regeneración pasiva.
- No existe gasto permanente de coherencia.
- El consumo se deriva del estado y de la configuración.
- El estado del modo estándar no se modifica.

La interfaz muestra coherencia mediante:

- Número usado/disponible.
- Segmentos visuales.
- Etiqueta accesible actualizada.
- Información junto a cada jugador.

5.3. Vista previa de capturas cuánticas

- Las acciones complejas muestran un árbol de resultados antes de confirmar.
- Se presentan atacante, defensor, probabilidades y consecuencias posibles.
- El resultado nunca depende solamente del color.

6. IMPLEMENTACIÓN REALIZADA: IA Y TUTOR
======================================================================

6.1. IA cuántica

- Ejecuta la búsqueda en un Web Worker.
- Se puede cancelar cuando cambia la posición o se abandona la partida.
- Tiene presupuestos de tiempo por dificultad.
- Admite semillas reproducibles.
- Ordena acciones de forma determinista cuando las evaluaciones empatan.
- Enumera movimientos clásicos, split, fusión, túnel, enroque y capturas.
- Usa heurística local incluso si Stockfish no está disponible.

Se corrigió además un problema real de estabilidad: la identidad cambiante del
objeto de sonido reiniciaba el efecto del Worker y podía cancelar la respuesta
de la IA. Los efectos y callbacks relevantes quedaron estabilizados.

6.2. Tutor clásico

- Utiliza Stockfish MultiPV.
- Calcula pérdida aproximada en centipawns.
- Clasifica jugadas como mejor, excelente, buena, imprecisión, error o blunder.
- Detecta motivos deterministas básicos como captura, jaque y enroque/seguridad.

6.3. Tutor cuántico

- Ordena candidatos legales reproducibles.
- Expone evaluación, probabilidad y conceptos relacionados.
- Considera material esperado, seguridad, ramas y coherencia.
- Usa claves de explicación localizadas.
- No envía partidas ni posiciones a modelos generativos.

7. IMPLEMENTACIÓN REALIZADA: REPLAYS Y ANÁLISIS
======================================================================

- Los replays terminados se guardan como acciones neutrales al idioma.
- No se persisten títulos ni descripciones traducidas como fuente de verdad.
- Las mediciones incluyen sus rolls y resultados reproducibles.
- Los autosaves cuánticos conservan acciones y snapshots necesarios para
  reanudar exactamente.
- Los replays terminados se guardan en IndexedDB.
- Existe una cola de sincronización idempotente para cuentas vinculadas.
- Se creó la migración finished_replays con RLS de lectura propia.
- El análisis clásico usa Stockfish MultiPV cuando está disponible.
- El análisis cuántico usa candidatos locales deterministas.
- Se muestran clasificación, alternativas, conceptos y probabilidades.
- El usuario puede abrir el repaso educativo recomendado.
- Un replay puede ramificarse a un laboratorio “¿Qué habría pasado si...?”.
- La ramificación no modifica la partida original.

9. IMPLEMENTACIÓN REALIZADA: CUENTA, PRIVACIDAD Y APOYO
======================================================================

9.1. Cuenta opcional

La pantalla de Perfil incorpora:

- Enlace mágico por correo mediante Supabase Auth.
- Inicio OAuth con Google.
- Confirmación 13+ sin fecha de nacimiento.

9.2. Progreso append-only

- Los intentos tienen UUID.
- La cola offline es idempotente.
- Los reintentos no duplican dominio.
- Una cuenta vinculada puede enviar el identificador del invitado como origen.
- El backend recalcula el estado consolidado en lugar de confiar en snapshots.

9.3. Telemetría

- Es opcional y está desactivada por defecto.
- Usa una allow-list estricta.
- Solo admite ruta, lección, concepto, duración, puntuación y nivel de pista.
- Rechaza campos adicionales como estado de tablero o texto personal.
- Los datos funcionales no dependen del consentimiento analítico.

9.4. Membresía de apoyo

- Existe una tarjeta de apoyo en Perfil controlada por feature flag.
- Solo acepta URLs HTTPS válidas de Stripe Checkout.
- El texto deja claro que educación, reglas, tutor, retos y competitivo siguen
  siendo gratuitos.
- Todavía no hay webhooks ni entrega real de entitlements; esa parte está
  pendiente y el flag permanece apagado.

14. QUÉ QUEDA PENDIENTE DE IMPLEMENTACIÓN
======================================================================

14.1. Núcleo de juego compartido

- Extraer reglas, RNG, hashes y validación a un paquete TypeScript puro.
- Consumir el mismo paquete desde navegador, Worker y servicio autoritativo.
- Ejecutar pruebas de equivalencia contra classic y quantum-standard.
- Evitar cualquier divergencia entre cliente y servidor.

14.2. Servicio TypeScript autoritativo

- Crear el servicio Node/TypeScript separado.
- Recibir únicamente acciones, nunca snapshots.
- Persistir partidas y eventos en Supabase mediante service_role.
- Implementar relojes de servidor.
- Pausar ambos relojes durante medición con máximo de 15 segundos.
- Añadir reconexión por afterVersion.
- Hacer idempotentes todos los reintentos.
- Migrar las salas casuales desde el sistema legacy.
- Dejar terminar las salas antiguas antes del corte.

14.3. Persistencia Supabase real

- Sustituir los repositorios en memoria de la API v1.
- Implementar el adaptador de progreso.
- Implementar el adaptador de replays.
- Implementar retos diarios validados online.
- Implementar analítica consentida.
- Implementar perfiles, logros y rachas consolidados.
- Probar migración y deduplicación entre dos dispositivos reales.
- Probar exportación y borrado contra la base remota.

14.4. Online cuántico

- Validar todas las acciones cuánticas desde el núcleo compartido.
- Sincronizar mediciones y RNG desde servidor.
- Resolver acciones simultáneas y versiones obsoletas.
- Probar cortes de red, reintentos y reconexión.
- Ejecutar simulaciones concurrentes sin divergencias.
- Abrir primero una beta casual no clasificada.

14.5. Competitivo

- Implementar cola Coherencia limitada 10+5.

- Validar abandono, timeout y reconexión.

14.6. Stripe y cosméticos

15. PASOS IMPRESCINDIBLES QUE DEBES HACER ANTES DE LA SIGUIENTE FASE
======================================================================

No necesitas programar nada. Lo importante es preparar infraestructura, accesos
y decisiones de producto.

PASO 1. ELEGIR EL OBJETIVO DE LA SIGUIENTE FASE

Recomendación:

1. Primero Supabase staging y persistencia real.
2. Después núcleo TypeScript compartido y online casual autoritativo.
3. Después beta cerrada y carga.
4. Después competitivo.
5. Stripe puede hacerse en paralelo o posponerse.

Indícame si quieres seguir este orden o si Stripe debe adelantarse.

PASO 2. CREAR UN PROYECTO SUPABASE DE STAGING

Debes tener:

- Un proyecto separado de producción.
- Project ref.
- URL del proyecto.
- Publishable key o anon key.
- Service role key guardada únicamente en backend/hosting.
- Una contraseña de base almacenada de forma segura.

No envíes estas claves en el chat.

PASO 3. INSTALAR DOCKER DESKTOP

Es necesario para ejecutar Supabase localmente.

Después verifica:

docker --version
docker info

PASO 4. PREPARAR SUPABASE CLI

Desde la raíz del repositorio:

npx supabase@2.113.0 login
npx supabase@2.113.0 link --project-ref TU_PROJECT_REF

Para validar primero en local:

npx supabase@2.113.0 start
npx supabase@2.113.0 db reset

Revisa que las tres migraciones terminan correctamente.

Solo después, y trabajando sobre staging:

npx supabase@2.113.0 db push

No ejecutes db push sobre producción sin revisar previamente el diff y disponer
de copia de seguridad.

PASO 5. CONFIGURAR SUPABASE AUTH

En el dashboard de staging:

- Activar usuarios anónimos si se desean invitados online.
- Activar correo/enlace mágico.
- Configurar la URL pública de la aplicación.
- Añadir URLs de redirección de localhost y staging.
- Crear credenciales Google OAuth.
- Configurar Client ID y Client Secret de Google dentro de Supabase.
- Probar magic link y Google con una cuenta de prueba.

Decide también:

- Si los invitados online estarán activos desde la primera beta.
- Qué ocurre si una persona enlaza dos invitados distintos.
- Cuánto tiempo se conservará una cuenta borrada en backups.

PASO 6. CREAR LOS ARCHIVOS DE ENTORNO PRIVADOS

Copia:

.env.example              -> .env
frontend/.env.example     -> frontend/.env

Configura al menos:

Backend:

- SUPABASE_URL.
- SUPABASE_PUBLISHABLE_KEY.
- STOCKFISH_POOL_SIZE.
- STOCKFISH_QUEUE_TIMEOUT.
- FEATURE_AUTHORITATIVE_QUANTUM=0.

Frontend:

- VITE_API_BASE.
- VITE_SUPABASE_URL.
- VITE_SUPABASE_ANON_KEY.
- Los flags de Academia, sincronización, diario y Coherencia.
- VITE_FEATURE_SUPPORTER=0 hasta completar Stripe.

Para la futura persistencia del servicio será necesaria una variable privada
SUPABASE_SERVICE_ROLE_KEY en el backend. No debe llevar prefijo VITE_ y nunca
debe llegar al navegador.

PASO 7. DECIDIR DÓNDE DESPLEGAR EL SERVICIO TYPESCRIPT

- Región principal.

- Número inicial de instancias.
- Límite de CPU/memoria.
- Si FastAPI y el servicio TypeScript estarán separados.

Recomendación técnica:

- React PWA como frontend estático.
- Servicio TypeScript autoritativo separado.
- FastAPI separado para Stockfish/análisis.

Comunícame la decisión y, si existe, el nombre previsto de cada servicio.

PASO 9. PREPARAR STOCKFISH PARA CARGA

Debes decidir:

- Cuántos análisis simultáneos soportará el plan de hosting.
- Tiempo máximo aceptable de cola.
- Profundidad/presupuesto por tipo de usuario.
- Si el coach se limita por usuario o IP.

Empieza con:

- Pool de 2 procesos.
- 1 thread por proceso.
- Hash limitado.
- Timeout de cola de 3 segundos.

Estos valores se ajustarán tras las pruebas de carga.
